## 2. Semver rationale

Per [semver.org](https://semver.org) (v2.0.0):

- **§7 — MINOR "MUST be incremented if new, backward compatible functionality is introduced
  to the public API."** The 28 releases above that added MCP tools/params, CLI commands, SDK
  methods, or env-flag-gated behaviour all introduced new backward-compatible functionality.
  Every one of them should have been a MINOR bump. Examples: 3.4.12 (`memory_query`),
  3.4.34 (`ar corrections export`), 3.4.39 (SDK composite API), 3.4.42 (working-memory
  tier), 3.4.51 (four new CLI commands).
- **§8 — MAJOR "MUST be incremented if any backward incompatible changes are introduced to
  the public API."**
  - **3.4.49** is the clear-cut case: public SDK/core methods changed from sync to async
    (`digestInvalidate()`, `markStale()`) and public functions were **removed**
    (`withLockSync`, `acquireLockSync`, `markStaleAsync`). For any consumer of
    `agent-recall-sdk`/`-core`, that is a compile/runtime break. Strictly, 4.0.0.
  - **3.4.36** deleted 11 `--full` MCP tools and changed the documented default `session_end`
    verdict from `heeded` to `unknown` (C3). If the MCP tool surface is considered public API
    (it is the product's primary interface), §8 says MAJOR; at absolute minimum it is a
    MINOR with a deprecation cycle, not a patch. The usage census ("zero organic use across
    2,649 transcripts") is a good reason to delete, not a reason to call it a patch.
  - **3.4.13** (default tool surface 11 → 6) is the same class in milder form: consumers of
    the default surface lost tools, with `--full` as escape hatch → MINOR with a loud
    behaviour-change note was the floor.
- **Behaviour changes that deserved at least a MINOR + upgrade note**: 3.4.44 (scrubbing
  semantics at every surface), 3.4.45 (all four delivery channels now wrap memory in
  `⟦agentrecall:memory⟧` fences — anything parsing raw output sees new delimiters), 3.4.49
  (hot-window recency boost neutralized — ranking visibly changes), 3.4.51 (`retier`
  enforcement ladder; KPI surfaces now show a two-number heed split).
- §6 (patch = backward compatible **bug fixes** only) was genuinely respected by roughly a
  third of the line (3.4.1–2, 4–7, 14, 22, 26, 44, 46 and similar).

**Honest paragraph for README/CHANGELOG (paste-ready):**

> **A note on 3.4.x version numbers.** The 3.4 line carried 51 patch releases, and many of
> them were not patches: new MCP tools, new CLI commands, new SDK methods, and two releases
> our own changelog labelled "breaking" (3.4.36, 3.4.49) all shipped as patch bumps. The
> cause was process, not carelessness — minor bumps were gated on owner approval, so feature
> waves kept landing on the only increment that wasn't. That reads as semver abuse from the
> outside, and we're fixing the process rather than the history: nothing in 3.4.x is being
> re-released or renumbered. From 3.5.0 on, new functionality bumps MINOR, bug fixes bump
> PATCH, breaking changes bump MAJOR, and every release ships with notes. The gate stays —
> the owner still approves every publish — it just no longer forces features into patches.

## 5. Process proposal (≤10 lines)

1. New functionality → **MINOR**; bug fix → **PATCH**; anything backward-incompatible → **MAJOR** (semver.org §6/§7/§8). "It's small" is not a patch criterion; compatibility is.
2. `npm version` is run **only by the owner** (REDLINE unchanged) — but the owner picks the increment the diff dictates, not the increment the gate allows.
3. **CI green (incl. windows-latest) is a hard precondition** for `npm publish`.
4. Every tag gets notes: `gh release create vX.Y.Z --notes-file ...` in the same session as the publish — no more stub "Full Changelog" bodies.
5. Every release gets a CHANGELOG.md entry **before** the tag (3.4.37 and 3.4.51 both shipped without one).
6. Prereleases via dist-tag: `npm publish --tag next`; `latest` only moves on stable.
7. All four packages publish in lockstep at the same version (3.4.x skipped numbers per-package; see §1).
8. Publish order when lockstep: core → mcp/cli/sdk (dependents after dependency).
