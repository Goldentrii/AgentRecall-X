# A13 — win32 rename-retry test fails on the GitHub Windows runner

**Branch:** `fix/rename-retry-budget` (from main @ 4315e9d)
**Scope:** `packages/core/src/storage/fs-utils.ts` (renameAtomic budget), `packages/core/test/fs-utils-rename-retry.test.mjs` (deterministic on slow runners)

## Failure

CI run 38251553161, `test (windows-latest)` — the lane's only red:

```
not ok 1 - writeTextAtomic rides out a no-delete-sharing reader holding the destination
  duration_ms: 9029.5007
  error: "EPERM: operation not permitted, rename '…\alignment-log.json.tmp.4420' -> '…\alignment-log.json'"
```

A11's `renameAtomic` (067bf16) retried with 1→512ms exponential backoff, ~1023ms
total requested sleep, then rethrew. The test's PowerShell reader held the
destination for an intended 400ms after signaling `HOLDING`.

## Root cause

Two findings, one mechanism:

1. **Readiness sync already existed** — the writer only starts after the reader
   prints `HOLDING` with the handle open, so slow PowerShell *startup* (1–3s on
   the runner) was NOT the defect. (It was still a latent hazard: no startup
   timeout meant a wedged child would hang the suite; fixed below.)
2. **The hold-to-budget ratio was the defect.** The reader's *release* is
   `Start-Sleep 400ms; $f.Close()` — wall-clock drift on a loaded 2-vCPU runner
   stretched that past the writer's entire ~1023ms budget. The failing test's
   9s duration shows how starved the box was. 400ms hold vs ~1s budget is only
   2.5× headroom; the drift alone exceeded 620ms.

### Measurements (this PC, Ryzen desktop, idle — the FAST case)

Reader with intended 400ms hold, 5 runs:

| metric | values (ms) |
|---|---|
| spawn → HOLDING (handle open) | 258, 255, 265, 310, 297 |
| HOLDING → process close | 477, 476, 479, 499, 477 |
| close drift vs intended 400ms | +77, +76, +79, +99, +77 |

Even idle on a fast machine the close drifts ~+80ms (20%). On the CI runner the
same drift multiplied under scheduler pressure past the whole remaining budget.

## Red (reproduces the CI failure locally)

Against the OLD production code, a reader whose hold drifts to 2000ms (what the
runner effectively did to the 400ms hold):

```
RED: EPERM after 1140ms — budget gave up before the holder released
```

## Fix

### Production: budget ~1s → 5s (`RENAME_RETRY_BUDGET_MS`, exported)

- Backoff 10→250ms doubling, then flat 250ms until exactly 5000ms of
  *requested* sleep is spent (counting requested sleep, not wall clock, so a
  descheduled process still waits at least the full budget), then the original
  EPERM/EACCES/EBUSY is rethrown. Still win32-only; non-transient codes and
  POSIX rethrow immediately as before.
- **Why 5s:** (a) A11's observed alignment-log flake windows were ms-scale
  reader handles, but the class of real holders includes antivirus/indexer
  scans that commonly pin a just-written file for 100ms–2s — 1s had no margin
  over the top of that range, 5s has 2.5×; (b) CI empirically stretched a
  400ms-intent holder past 1s, so the old budget was ALREADY losing to real
  schedulers, not just hypothetical AV; (c) the 5s worst case is only paid when
  the rename is genuinely blocked the entire time — uncontended renames (the
  overwhelmingly common case) succeed on attempt 1 with zero sleep, and a
  blocked-then-released rename lands ≤250ms after release (the cap).
- Exported so the test derives every duration from the real value — the test
  and the budget can never drift apart again.

### Test: deterministic regardless of runner speed

- **Transient holds 400/300ms → 1500ms** (`TRANSIENT_HOLD_MS`): >3× headroom
  under the 5s budget, so a couple of seconds of runner-induced close drift
  stays transient instead of flipping the test red.
- **Waited-it-out proof:** elapsed-to-landing is measured immediately after the
  write returns (NOT after the reader-exit await, which spans the hold by
  itself and would mask a write that snuck through early) and must be
  ≥ hold − 700ms epsilon. The HOLDING→first-rename gap is a few syscalls and
  close drift is always late, so sub-800ms landing means the window was never
  ridden out.
- **Persistent case:** reader holds budget + 2500ms; asserts EPERM surfaces,
  `took` ≥ budget − 100ms (requested-sleep accounting makes wall time ≥ budget)
  and `took` < hold − 1000ms (gave up while genuinely still held — which the
  successful `assert.throws` also proves, since a released holder would have
  let the rename succeed). Test timeout = 3 × (hold + budget) = 37.5s;
  transient tests 60s.
- **Error paths traced:** spawn `error` rejects; child exiting without
  `HOLDING` rejects with stderr; NEW 30s startup watchdog kills a silent child
  and rejects (previously: hang); NEW 30s exit-grace watchdog kills a wedged
  reader in `finally` so afterEach's rmSync never races a held handle. Single
  `settle()` gate so watchdog/resolve/reject can't double-fire.
- **Linux skip is now named:** `skip: "win32-only: exercises NTFS
  no-share-delete rename semantics via powershell.exe"` (was a bare boolean).
