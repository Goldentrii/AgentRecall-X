## Summary: NEEDS_FIXES

ADR-002 is well-structured on paper (state machine, thresholds, disclaimers) but two of the eight attack vectors land on genuinely load-bearing gaps: (a) the "verifier" role that gates auto-activation has zero contract-level definition and the ValidationReport's safety-critical fields are self-reported with no specified cross-check, and (b) the four "reuse, not rebuild" modules this ADR leans on for the A28 guarantee do not currently touch the `authority`/`MemoryRecord` model at all — grep across all four returns zero hits. Several other vectors (lineage independence, fencing/backup divergence, A29 scope) surface real but narrower gaps. No uplift overclaim found.

## Blocking

1. **"Verifier" role is prose, not contract.** `GrantSpec` (frozen `packages/core/src/repository/contract.ts:406-415`) has only `can_read/can_write/can_approve/personal/expires_at` — no `verifier` field, no `Role` type anywhere in `contract.ts`, `adr/contracts.md`, or `adr/contracts-rev2.md`. ADR-002 §4/§5 talk about "a dedicated grant flag `verifier`" and "role `verifier`" that `evolution-contract.ts` (a file ADR-002 fully owns pre-freeze) never actually types. `Principal` has no role field either. As written there is nothing for a driver to type-check against.
   `required_fix`: add a typed `Grant`/role surface in `evolution-contract.ts` itself (e.g. `verifier: boolean` alongside an explicit rule that only a `can_approve=true` principal may issue it), since `contract.ts` is off-limits but this file is not.

2. **Validation gate checks shape, not substance — collusion is not actually blocked.** The contract's own comment says it plainly: *"Pure gate check; the driver still verifies registry membership and principal separation"* (`evolution-contract.ts:69`). Nothing requires the driver to recompute `independent_sources` via the sibling method `independentSources()` and compare it to the report's self-reported number; nothing requires re-running the registered held-in/held-out suite to verify `regressions`, `misapplications`, `hard_safety_failures`, `scope_leak`, `secret_leak` against ground truth. "Cannot author candidates in the same lineage" (§5) only forbids same-principal self-validation *within one lineage* — it does not forbid two principals controlled by the same owner/automation acting as learner-in-lineage-A / verifier-in-lineage-B and vice versa (cross-lineage mutual rubber-stamping), because verifier-grant issuance rules are unspecified (see #1).
   `required_fix`: mandate the driver independently recompute `independent_sources` from real `source_event_ids` and reject on mismatch; require held-in/held-out counts to reference an auditable re-derivable proof artifact (test-run log hash), not bare integers; scope "cannot author in same lineage" to "cannot hold a learner grant in the same workspace/project the candidate came from."

3. **A28 is asserted about code that does not implement it.** `packages/core/src/tools-logic/retier.ts`, `implicit-harvest.ts`, `association.ts`, `packages/core/src/retrieval/activation.ts`, and `session-end.ts`'s `promoteConfirmedInsights` (→ `insight-promotion.ts`) contain **zero** occurrences of `authority`, `explicit_user`, or `legacy` — they operate entirely on the pre-ADR-001 `corrections.ts` model (`severity` p0/p1, `proof_confidence`, `weight`, `provenance.mode`), a disjoint system from `MemoryRecord.authority`. ADR-002 §1 states in the present tense: *"Decay/retier/activation code paths filter authority ∈ {explicit_user, legacy} out of every mutation they perform (A28)"* — this is not true of the actual source, and §8's four "changes:" bullets never describe the porting work needed to make it true. A28's own setup fixture in ACCEPTANCE.json explicitly exercises `retier/activation/rebuild` against `explicit_user` constraints, which today these modules cannot even see.
   `required_fix`: either (a) specify the concrete adapter/porting design that adds an authority filter at each module's actual write call site, with an owner and exit criterion, or (b) state explicitly that `kind=experience` is a wholly new, separate store from legacy `corrections.ts` and reconcile that with A28's fixture, which assumes these specific modules run against `authority`-typed records.

4. **A29 claimed in scope, not addressed in body.** ADR-002's scope line lists A29, whose setup includes "旧p0记录" (old p0 records) and pass_standard requires "其他为candidate/legacy" migration handling. The ADR body never mentions legacy-authority migration for old corrections records at all — only the new experience state machine going forward.
   `required_fix`: either add an explicit paragraph on how pre-existing p0/corrections records map to `authority=legacy` (not `explicit_user`), or drop A29's migration half from this ADR's claimed scope and point it at the P3/P4 migration ADR instead.

5. **Fencing token / lease-store divergence under backup restore is unaddressed.** §7 says fencing tokens are rejected if "lower than the highest seen for that scope," but never states whether that high-water-mark is anchored in the same transactional/backup boundary as the repository it fences. Local ("lease file under repo lock") is plausibly co-restored; cloud ("`ar2_leases` row + RPC") is not shown to be in the same backup domain as `ar_entries`/experience tables. PLAN §11.2's rollback-drill list ("worker故障") doesn't name this scenario either.
   `required_fix`: state explicitly that lease/fencing state MUST share a backup/restore boundary with the repository, or define a reconciliation step that recomputes per-scope high-water-marks from the repository's own committed mutation history after a lease-store restore; add this as a named §11.2 drill.

6. **Lineage-root independence has no anti-gaming floor, and the ADR silently drops PLAN's own caveat.** `independentSources()` only counts distinct `lineage_root` values among caller-supplied `source_event_ids` — nothing requires those roots come from different principals, different time windows, or tasks of any minimum substance. PLAN §6.3 itself says *"3 个来源是保守的工程门槛，不是统计证明"* — ADR-002 §4 uses "≥3 independent sources" as a hard gate for **auto-activation** (a security-relevant decision) without carrying that caveat forward, so a reader of the frozen ADR would reasonably treat it as a stronger guarantee than intended.
   `required_fix`: restate the PLAN caveat directly next to the auto-activation clause in §4, and/or add a minimal floor (distinct principal_id or minimum time separation) before this count is allowed to gate auto-activation specifically.

## Non-blocking

- Rollback correctly refuses to resurrect retracted content (`rejected:retracted`) and is idempotent per operation_id — good. Not stated: propagation latency for a session already mid-flight with the bad `active_version` injected before the rollback lands (general freshness envelope may cover this, but not called out for evolution specifically).
- "A used held-out set is burned for that lineage" is ambiguous — could mean the set is retired globally, or only unusable again *by that lineage* (leaving it reusable by a sibling lineage under the same operator, enabling slow cross-lineage probing via the per-attempt granular counts `non_applicable`/`misapplications`/`hard_safety_failures` that ValidationReport exposes). Clarify wording and consider capping retry attempts per lineage before forcing owner review or coarser (pass/fail-only) report visibility back to the learner.
- `RunReport`/`ExperienceRepository` cover cost/token/dry-run/NO_ELIGIBLE_DATA well, but there is no typed checkpoint/cursor object for `ar evolve resume` — resume safety is left to ad hoc per-driver bookkeeping plus operationId idempotency, risking local/cloud resume-semantics drift.
- §9 "Not claimed" correctly scopes the ADR to mechanism-only; no uplift overclaim found in the text.

## Compound lessons

1. When an ADR states an invariant as already enforced by named existing modules, grep those modules before trusting the prose — `retier.ts`, `implicit-harvest.ts`, `association.ts`, `activation.ts` contain zero occurrences of `authority`/`explicit_user`, directly contradicting ADR-002 §1's present-tense A28 claim.
2. A validation gate that checks report *shape* (hash membership, principal-id inequality) but never re-derives report *substance* (`independentSources()` exists on the same interface yet is never wired into `attachValidation`'s pass path) is not a collusion boundary — it's a paperwork boundary.
3. "This file is reserved for ADR-002" is permission to define new types, not an excuse to leave a role ("verifier") as prose — `evolution-contract.ts` was free to add a `Grant`/role type and didn't, while `GrantSpec` in the genuinely-frozen `contract.ts` correctly has none.
