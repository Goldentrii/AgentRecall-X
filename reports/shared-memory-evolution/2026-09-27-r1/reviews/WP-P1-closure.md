## Node-defect claim verdict: **TRUE** (well-supported by independent reproduction)

I did not find the author's specific "minimal driver-free repro" file committed anywhere in the worktree (it's described as a throwaway, matching their own stated practice elsewhere), so I built my own from scratch and cross-checked against the real suite.

1. **Reproduced the real hang location myself, fresh**, on Node v24.11.1 (matches the environment exactly): ran `scripts/acceptance/contract-suite.mjs` against the fix-round's own `local-harness.mjs` (no author involvement, full 174s run). Result: 59 pass / 1 fail / 1 cancelled, exactly matching the report. The one failure is `G-authz > agent-created constraint is a candidate, not active`, which times out at exactly 60000ms (`failureType: 'testTimeoutFailure'`) — the subtest immediately after "narrowing", exactly where WP-V's own `WP-V-report.md` ("Fix round 2") independently recorded **both** real drivers (P1's file-based AND P2's separately-built pglite-based) hanging identically, pre-dating any of P1's own fixes.
2. **Ruled out "coincidence across two drivers implies a real shared driver bug"**: ran the same suite/group against `scripts/acceptance/fixtures/naive-harness.mjs` (a trivial in-memory driver with zero real logic). It does **not** hang — it fails fast with a normal `AssertionError` at the exact same line, because naive's wrong behavior (`effective_status:"active"` instead of `"candidate"`) throws *before* the code ever reaches the nested `t.test(...)` call. This fully explains why only "correctly-behaving" real drivers (both P1's and P2's) hit the hang: they pass the outer assertions and proceed into the vulnerable nested-test shape; naive never gets there.
3. **Built a minimal, zero-import, zero-driver repro** (`test() → t.test() → t.test()`, inner test awaited as the tail of the middle test's body, no parameter passed to the nested call — the exact shape `armGroupTimeouts`/G-authz uses): it hangs for the full declared timeout on this machine, on Node v24.11.1, with **no application code involved at all**. A control variant with only 2 levels (`test() → t.test()`, no further nesting) completes in ~1ms. This isolates the defect to nesting *depth* specifically, not to anything about the driver.
4. Minor caveat: my minimal repro's exact failure signature (`cancelledByParent` on both levels) doesn't byte-for-byte match the real suite's signature (inner subtest reports `ok` in 5.9ms while the outer alone times out) — likely a timing/ordering nuance of `armGroupTimeouts`'s wrapper I didn't replicate exactly. This doesn't change the verdict, since the core claim (3-level `node:test` nesting can hang independent of driver code, on this exact Node version) is independently confirmed twice, once against the real suite/driver and once with a clean-room repro.

Verdict: **TRUE** — this is a real `node:test`-runtime scheduling defect for 3-level-nested subtests on Node v24.11.1, not an excuse for a driver bug. WP-V's own mitigation (per-test timeout + watchdog) correctly contains it to one bounded FAIL rather than a stuck process, exactly as designed.

## New defects (from the "6 extra bugs fixed" this round)

Checked all six for weakened guarantees; five are clean, additive fixes (verified: `existence-hiding` gate, `__proto__` metadata-before-hash ordering, `list()`/`recordOutcome()` harness forwarding, `derived_closure` overflow-withheld, and the `before_receipt` recovery no-longer-minting-a-receipt fix all hold up under direct code reading + their own tests, no regression found). One item needs explicit sign-off, not a code fix:

- **MEDIUM — `history()`'s retraction "tombstone" is asymmetric and not itself spec'd.** Only the *final* (retracted) revision gets `content:""`; every *prior* (pre-retraction) revision keeps its full original content, forever, via `history()`, to anyone who can read the record's scope — even though `get()`/`query()`/`list()`/`export()` all say the record "doesn't exist." The frozen `G-retract` suite doesn't test content on either revision, so this passes the acceptance gate, but it's a self-authored design choice, not a contract requirement. If "retract" is ever used for actual redaction (PII, wrong info), this leaves the original content permanently recoverable by anyone with read standing on that record's scope via `history()`. Recommend an explicit ADR/PLAN sign-off on retraction-audit-trail semantics (should revision 1's content also be redacted, or is full pre-retraction history genuinely intended?) before this becomes load-bearing for P3/P4 UI.
- Checked but not a regression: the existence-hiding relaxation (`hasAnyStanding` vs `canRead`) is correctly scoped to the *mutation* path only (`mutateLocked`'s not_found gate); `get`/`query`/`history`/`list`/`export` are untouched and still gated by `canRead()` alone, and `ConflictReceipt.current` still separately requires `canRead()`. No weakening of R2.3 for a caller with zero standing.
