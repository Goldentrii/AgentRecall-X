## Summary: NEEDS_FIXES

Build is clean (`tsc` x4, 0 errors), all 22 new WP-P1 tests pass when I ran them directly, the RED→GREEN commit history is real, Case B and the 60-call isolation test are genuine (not staged), no frozen/forbidden files were touched, and the `package.json` exports deviation is safe/additive. However, I found **5 confirmed, reproduced bugs** the author's own test suite does not exercise — one is a real path-traversal / arbitrary-file-read vulnerability, one is a silent authorization-matrix deviation, two are commit-protocol atomicity/durability gaps, and one is an existence-hiding leak. None of these are hypothetical; I wrote small repro scripts against the built `dist/` and confirmed all five against the actual code.

## Blocking

**1. Path traversal via unvalidated `id` in `LocalRepository.get()` / `history()` (CRITICAL, security)**
File: `packages/core/src/repository/local/local-repository.ts:97-99` (`recordPath`/`historyDir`), `:419-432` (`get`), `:472-487` (`history`).
`get(id, ctx)` and `history(id, ctx)` are public `MemoryRepository` methods that take a bare `id: string` straight from the caller and feed it into `path.join(this.repoDir, "records", `${id}.json`)` / `path.join(this.repoDir, "history", id)` with **no `isUuid()` check** — unlike `mutate()`, which always runs `validateCommand()` (which does call `isUuid(cmd.id)`) before touching a path. This directly contradicts the brief's own stated invariant ("ids only via isUuid... before any path.join") and contract.ts's R2.13.
Reproduced: planted a JSON file shaped like a `MemoryRecord` at `<root>/repo/planted-secret.json` (outside `records/`), then called `rt.repository.get("../planted-secret", ctx)` — it returned the planted file's content as `items[0]`, i.e. an out-of-directory arbitrary-file read, gated only by the target file's ability to parse as JSON and loosely match a record shape (any file with `status`/`visibility` fields set appropriately). For an owner-principal caller, `canRead()`'s owner short-circuit (`policy.ts:118`) accepts *any* visibility value, so the shape bar is very low.
Fix: call `isUuid(id)` (or throw/`not_found`) at the top of `get`, `history`, and any other read/write entry point that takes a bare `id` before it reaches `recordPath`/`historyDir`/`historyPath`.

**2. `policy.ts` silently drops R2.1 row-2's visibility-triggered candidate gating for non-constraint kinds (HIGH, authorization)**
File: `packages/core/src/repository/policy.ts:171-177` (`statusForCreate`), called from `:224-236` (row-2 branch of `authorize()`).
R2.1 row 2 (contracts-rev2.md line 14) is an OR of three triggers — `kind = constraint`, OR `visibility in {workspace, owner_shared}`, OR project mismatch — landing on ONE cell: "can_write -> status candidate; owner_trusted -> active", with no kind-based carve-out. `statusForCreate()` only implements the candidate-gate for `kind === "constraint"`; for every other kind it unconditionally `return "active"`, citing rev1 §4.2's "active for fact/decision/preference (non-gating)" — but rev1 §4.2 predates the visibility trigger entirely, and the freeze rule explicitly says rev2 wins where they differ.
Reproduced: `authorize({ op:"create", trusted:false, create:{ kind:"fact", visibility:"workspace", ... }, grants:[can_write, not can_approve] })` → `{ kind:"allow", effectiveStatus:"active" }`. An agent with only a `can_write` grant (no owner trust) can publish a workspace-wide (or `owner_shared`) fact/decision/preference/experience/handoff as immediately `active`, bypassing the owner-review gate the contract explicitly requires for that visibility class.
Not covered by any test: there is no `policy.ts` unit test file at all, and no `repo-local-core.test.mjs`/harness test uses `visibility: "workspace"` or `"owner_shared"` for any kind (grep confirmed zero occurrences).
Fix: `statusForCreate` needs the triggering visibility (or a `isRow2`-and-not-constraint flag) as an input, not just `kind`.

**3. Repo lock stale-reclaim is time-only with no liveness/ownership check — breaks the single-writer invariant under realistic (not just crashed) slow commits (HIGH, data integrity)**
File: `packages/core/src/repository/local/lock.ts:14-22,45-54`.
`STALE_LOCK_MS` was intentionally lowered to 2000ms (from 15000ms) specifically so a crash-abandoned lock is reclaimed inside `LOCK_MAX_WAIT_MS` (8000ms). But `reclaimIfStale()` only checks the lock file's mtime — it never checks whether the holding process is actually still alive (no PID+liveness probe), and the lock file itself carries no owner token that `withRepoLock`'s `finally { fs.unlinkSync(p) }` verifies before deleting. If a *legitimate, non-crashed* critical section (e.g. `mutateLocked`, or `recoverWal()` replaying a large WAL backlog on a slow disk / AV-scanned Windows machine) takes ≥2s, a second process will conclude the lock is abandoned, delete it, and acquire its own lock — now **two processes execute the commit protocol concurrently**, sharing the same `SEQ` file, `records/`, and `ops/` receipt store with zero exclusion between them. Worse: when the first (still-alive) holder finishes, its `finally` unconditionally `unlinkSync`s whatever lock file is currently there — which is now the SECOND process's lock — so a THIRD process can then race in while the second still believes it holds exclusivity.
This is exactly what item 3 of the brief asked to check ("CAS race under 2 processes, not just 2 promises") and it is not exercised by any test — the WAL-recovery tests only simulate a hard `process.exit(137)` crash, never a slow-but-alive holder.
Fix: lock file needs an owner token (pid+random nonce) checked on both `reclaimIfStale` (verify the pid is actually dead, e.g. via `process.kill(pid, 0)` throwing ESRCH — imperfect but far better than a bare timer) and on release (only unlink if the file's content still matches this holder's token).

**4. Two-record mutations (`supersede`, confirm-of-proposal) are not atomic across their two `commitRecord()` calls, and a crash between them causes silent, unrecoverable data loss on retry (HIGH, durability)**
File: `packages/core/src/repository/local/local-repository.ts:747-776` (`doConfirm`, proposal-apply branch), `:778-808` (`doSupersede`).
Both methods do `commitRecord(A, ..., { hash, actorPrincipalId })` (the CALLER's real `operationId`, writing the durable idempotency receipt at `mutateLocked`'s replay key) **then** `commitRecord(B, ..., { actorPrincipalId })` (a second, unrelated `innerOpId`, no `hash`, so it has no durable retry path tied to the caller's operation). If the process crashes between these two calls (still inside the same `withRepoLock` critical section, but each `commitRecord` is its own independent WAL cycle), the caller's real `operationId`'s receipt is *already durably committed* pointing at `A`'s new state — so a client retry with the same `operationId` hits `mutateLocked`'s idempotency short-circuit (`existingReceipt` found) and returns `{...existingReceipt, replayed:true}` **without ever attempting `B`'s write again**. Concretely: `supersede` can leave the original marked `superseded` with the replacement record permanently missing; confirm-of-proposal can leave the original applied but the proposal never marked `superseded` (a lingering duplicate candidate). This contradicts R2.5's "commit (record + event + operation in one transaction)" and the brief's "recovery idempotent" requirement — recovery here isn't idempotent, it's silently incomplete.
Not covered by any test: `repo-local-wal-recovery.test.mjs`'s two crash-fixture tests only exercise a single-record `create`; there is no crash test for `supersede` or confirm-on-proposal, and no `supersede` test exists in `repo-local-core.test.mjs` at all.
Fix: either wrap both record writes in one WAL entry (single intent covering both `record_after`s), or make the second commit itself replayable from the first's WAL entry during recovery (recovery must know to finish "B" when "A" is already committed but the logical operation is a two-record op).

**5. `history()` returns retracted-revision content, violating the driver's own stated existence-hiding/retracted-never-returned invariant (HIGH, information disclosure)**
File: `packages/core/src/repository/local/local-repository.ts:472-487`.
`get()`, `query()`, `readSnapshot()`, `list()`, `export()`, and `latestHandoff()` all route through `readAll()` → `readableStatusSet()`, which **never** includes `"retracted"` in its allowed set, even for a management-channel owner/`can_approve` read (`local-repository.ts:343-351`) — this correctly implements "retracted content is never returned" (A16) everywhere else. `history()` bypasses `readAll()` entirely and filters only by `canRead()`, with **no status filter at all**.
Reproduced: create → retract a `private` record as its own owner; `get(id)` correctly returns 0 items (existence-hiding); `history(id)` returns both revisions, including revision 2 with `status:"retracted"` and the full original content (`"secret v1"`) plus the retraction metadata — to the exact same owner caller who `get()` just told "this doesn't exist."
Not covered by any test: `repo-local-core.test.mjs`'s `history()` test only exercises three successive `update`s, never a retract.
Fix: `history()` needs the same status-based filtering `readAll()` applies (at minimum, exclude `retracted`; align with whatever `include_non_active`/`management` scoping is meant to gate `superseded`/`quarantined` visibility for history too).

## Compound lessons

1. **A "documented known limitation" is not the same as "the rest is verified correct."** The author correctly flagged one narrow R2.1 gap (project-mismatch trigger) but missed a second, more consequential one in the same row (visibility-triggered candidate gating for non-constraint kinds) that produces the opposite of the intended security posture. Self-disclosure of scope gaps should not be read as evidence the undisclosed parts were checked row-by-row against the frozen table — they need an explicit statement like "every row of R2.1/R2.2 has one test" or they should be assumed unverified.
2. **Zero-test modules are a standing invitation for exactly this class of bug.** `policy.ts` is pure, dependency-free, explicitly built to be "shared with WP-P2 as a reference" — the easiest possible module to unit test in isolation — and has no test file at all. Every authorization-matrix row that gates status/authority should have one direct assertion in a `policy.test.mjs`, independent of whatever paths the CRUD-style repository tests happen to hit incidentally.
3. **Crash-only fault injection (`process.exit(137)`) proves less than it looks like it proves.** All of this work's fault tests target a hard kill at two fixed points inside a *single*-record commit. Two of the five bugs found here (the lock race and the two-record atomicity gap) live specifically in the *multi-step, multi-process* and *multi-record* dimensions that a single-record single-crash-point test structurally cannot reach — "we have crash tests" and "the commit protocol is atomic under concurrency" are different claims, and the report conflates them.
