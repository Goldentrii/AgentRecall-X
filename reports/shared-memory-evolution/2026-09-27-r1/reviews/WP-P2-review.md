## Summary: FAIL

The RLS lockdown, CAS/idempotency ordering, and outbox mechanics are solid and well-tested. But `ar2_mutate` — the single most safety-critical function in this WP — has a real cross-project authorization bypass with zero test coverage, the client-side secret-scrub is dead code on the most common write path (`create`), the entire `ar_role` owner-trust claim has no minting mechanism against a real Supabase project, and two named spec invariants (R2.3 id-collision hiding, rev2.1 D3 exception-clearing) are implemented incorrectly or not at all. These are concrete, verified defects, not speculative — several directly contradict the WP-P2 report's own claimed "yes" answers in its SUCCESS_WHEN table.

## Blocking

**1. `ar_role='owner'` claim has no minting mechanism against real Supabase — owner-trust cannot function (or is silently forgeable, depending on how it gets patched next).**
Evidence: `migrations/0002_shared_memory.sql:22-23,685,714,741,846` all gate owner-trust on `auth.jwt() ->> 'ar_role' = 'owner'`. This is a flat, top-level JWT claim. Real Supabase JWTs do not contain this by default; it only appears if a **Custom Access Token Auth Hook** is registered in the Supabase project to inject it from a trusted server-side source. Nothing in this repo creates such a hook (`grep -rn "custom_access_token\|hook_uri\|access_token_hook"` → no matches; no `supabase/config.toml` anywhere). The test harness fabricates the claim directly from local `principal.kind` (`packages/core/test/harness/pglite-harness.mjs:77`: `ar_role: principal.kind === "user" ? "owner" : "agent"`), which proves nothing about production. As shipped: on real Supabase, `auth.jwt()->>'ar_role'` is always `NULL`, so `v_owner_trusted` is always `false` — every owner-gated action (`ar2_admin_grant`, `ar2_admin_revoke`, `ar2_admin_alias`, `confirm`, `exception`, `release_dependency`, `supersede`, protected-constraint retract) permanently rejects the real owner. The report's §7 "unverifiable" caveat undersells this: it's not "unverified," it's "unbuilt."
Required fix: ship the `custom_access_token_hook` Postgres function (deriving `ar_role` from a trusted table, e.g. workspace ownership) plus the Supabase project config/documentation to register it, or document this as an explicit pre-deployment manual step with a runbook — and add a test that fails if `ar_role` is ever read from `user_metadata`/`app_metadata` instead of the hook-issued top-level claim.

**2. `CloudRepository.mutate()` never actually scrubs content for `create` — the most common write path leaks secrets to Postgres unredacted.**
Evidence: `packages/core/src/repository/cloud/cloud-repository.ts:313-322`. `cleanCmd` is a shallow copy; for `op==="create"`, the code does `const c = cleanCmd as CreateCommand; c.content = scrubForCloud(c.content); c.metadata = stripReservedMetadata(c.metadata);` — mutating **`cleanCmd`**, a variable that is never used again. Line 331 (`payloadHash(cmd, expectedRevision)`) and line 335 (`this.callMutateRpc(cmd, ...)`) both reference the original, **unscrubbed** `cmd`. `scrubForCloud` (`packages/core/src/storage/content-guard.ts:98-114,167-175`) is the only layer that redacts AWS/GitHub/OpenAI/Slack tokens and PEM blocks before cloud egress, and there is no server-side equivalent in the SQL (`grep -n "scrub" migrations/0002_shared_memory.sql` → no matches). Note the `update`/`supersede` branches (lines 323-329) happen to work because they mutate `cmd.patch`/`cmd.replacement` in place (a different, milder bug: mutating the caller's own command object). No test catches this — the only scrub test is `export()`'s re-scrub (`packages/core/test/repo-cloud-surfaces.test.mjs:107-120`); nothing asserts a `create()` payload is redacted before it reaches the RPC/network.
Required fix: use `cleanCmd` (or reassign `cmd = cleanCmd`) for the `payloadHash`/`callMutateRpc`/outbox-enqueue calls; add a test that creates a record whose content contains `sk-...`/`AKIA...` and asserts the stored/queued content is redacted.

**3. `create` authorization never checks the caller's grant `project_ids` scope — cross-project write bypass.**
Evidence: `migrations/0002_shared_memory.sql:902-918`. The non-owner branch does `SELECT * INTO v_grant FROM ar2_active_grant(v_owner, v_workspace_id, v_caller); v_can_write := COALESCE(v_grant.can_write, false);` — this checks only the boolean `can_write`, never `p_cmd->>'project_id' = ANY(v_grant.project_ids)` (or `project_ids IS NULL`). Spec (`reports/.../adr/contracts-rev2.md` R2.1 row 1: "project_ids subset of grant | can_write | rejected:forbidden") explicitly requires this. Non-create ops (update/retract/etc.) are incidentally safe because they operate on a target row already gated by `ar2_visible`'s project check, but `create` has no pre-existing row to gate it. Consequence: an agent granted `can_write=true, project_ids=[A]` can `create` a `visibility="project"` record with `project_id=B` (a project it has no grant for in the same workspace), and it lands `active`, immediately visible to any other agent legitimately scoped to project B — a real cross-project data-injection/isolation bypass. No test: `packages/core/test/repo-cloud-rls.test.mjs:112-135` only exercises *read* scoping by `project_ids`, never write/create scoping (`grep -n "project_ids" packages/core/test/repo-cloud-*.test.mjs` confirms no create-side test).
Required fix: add `AND (v_grant.project_ids IS NULL OR (p_cmd->>'project_id')::uuid = ANY(v_grant.project_ids))` to the create-path `can_write` derivation (for `p_cmd->>'project_id' IS NOT NULL`); add a project-scoped-agent create-into-a-different-project test that asserts rejection or candidate-downgrade.

**4. R2.3 existence-hiding violated on `create` id-collision.**
Evidence: `migrations/0002_shared_memory.sql:919-923`: `IF EXISTS (SELECT 1 FROM ar2_records WHERE owner_id = v_owner AND id = v_id)` is a raw existence check with no `ar2_visible` gate, returning `rejected:schema, "id already exists"`. Spec (`contracts-rev2.md` R2.3): "Any id collision ... returns `rejected:not_found`, indistinguishable from a nonexistent id." A caller who cannot read the colliding record still learns something exists at that id. Low practical exploitability given random UUIDs, but it's a named, explicitly-tested-elsewhere invariant (`packages/core/test/repo-cloud-authorization.test.mjs:125-147` tests exactly this symmetry for `retract`, not `create`) that's silently broken for the one op where a client actually supplies the id.
Required fix: on collision, re-check `ar2_visible` against the existing row; return `not_found` when unreadable, keep `schema`/"id already exists" only when the caller can read it (still arguably should just always be `not_found` per the spec's literal wording — flag to orchestrator for the exact desired shape).

**5. rev2.1 D3 "clear exceptions[] on every non-exception revision" is not implemented.**
Evidence: the `update` (`migrations/0002_shared_memory.sql:1135-1196`), `retract`/`quarantine` (1007-1025), and `confirm` (1027-1069) branches all bump `revision` without ever resetting `exceptions = '[]'::jsonb`. Spec (`contracts-rev2.md` D3): "drivers enforce this by clearing exceptions\[] on every non-exception revision of T." Result: a stale, owner-approved exception (tied to an old `target_revision`) persists on the record after its content/applicability changes — exactly the staleness D3 was written to prevent. Zero test coverage of the `exception` op at all (`grep` confirms no test file references `op: "exception"`).
Required fix: add `exceptions = '[]'::jsonb` to every non-`exception` UPDATE of `ar2_records` inside `ar2_mutate`; add a test creating an exception, then updating the constraint, then asserting `exceptions` is empty on the new revision.

**6. R2.11 derived-closure cap (256) is exported but never enforced anywhere.**
Evidence: `packages/core/src/repository/contract.ts:453` defines `MAX_DERIVED_CLOSURE = 256`, but `grep -rn "256" packages/core/src packages/core/test migrations` shows it used nowhere — not in `validateRefs` (`contract.ts:461-469`, no length check), not in `ar2_derived_valid` (`migrations/0002_shared_memory.sql:289-327`, loops the full array unbounded), not in the create/supersede/update INSERT paths. Spec (R2.11): "cap 256; overflow -> withheld." Currently an over-256 `derived_from`/`derived_closure` array is accepted, stored, and iterated in full on every read with no overflow/withheld semantics.
Required fix: enforce the cap client-side in `validateRefs`/`validateCreateShape` (reject or truncate-with-flag) and/or server-side in `ar2_derived_valid` (`jsonb_array_length(p_derived_closure) > 256` → treat as invalid/withheld); add a test with a 257-entry closure.

## Non-blocking

- `ar2_strip_reserved_metadata` (`migrations/0002_shared_memory.sql:334-340`) does not mirror the rev2.2 `__proto__`/`constructor`/`prototype` stripping that `contract.ts:549-559` added after the WP-V finding, even though its own comment (`:329-333`) claims the DB is "the real trust boundary" precisely because it's reachable outside `CloudRepository`. Low direct Postgres-side risk (jsonb has no JS prototype semantics) but inconsistent with its own stated threat model for a direct-JWT attacker.
- `ar2_query`'s `LIMIT` (`migrations/0002_shared_memory.sql:520-549`) is applied to the `scoped` CTE *before* `ar2_derived_valid` filtering, so a page containing withheld derived records returns fewer than `p_limit` rows without backfill. `CloudRepository.list()`'s `next_page_cursor` logic (`cloud-repository.ts:213`: `items.length === limit`) then terminates pagination early, silently dropping remaining records whenever a page mixes valid and invalid derived records.
- `Outbox.drain()`'s catch-all (`packages/core/src/repository/cloud/outbox.ts:142-144`) treats any thrown error (including a genuine `PgError`, e.g. from `supersede`'s unchecked `v_new_id` unique-violation at `migrations/0002_shared_memory.sql:1106-1126`) the same as `NetworkError`/`TimeoutError` — retried then left "exhausted" forever, rather than terminal, unlike the live path's classification in `cloud-repository.ts:347-349`.
- `ar2_records.workspace_id` (`migrations/0002_shared_memory.sql:103`) has no FK to `ar2_workspaces(id)` (contrast `ar2_grants.workspace_id` at line 74, which does), relying solely on a create-time `EXISTS` check; deleting a workspace orphans its records.
- `CloudAdminRepository.grant/revokeGrant/setProjectAlias` (`admin-repository.ts:33-54`) derive `operation_id` from `ctx.session_id ?? randomUUID()`, but `ar2_admin_grant/revoke/alias` never consult `ar2_operations` — this idempotency plumbing is inert, and reusing `session_id` across two distinct grant calls in one session, or a bare network retry with a fresh `randomUUID()`, isn't actually deduplicated server-side.
- The report's honestly-disclosed RED-first deviation (§7) undersells its cost: item 2 above (`create()` scrub dead code) is exactly the class of bug a committed-RED test ("create with a secret → assert redacted before send") would have caught immediately; it and items 3/5/6 above suggest the deviation had a real, measurable price beyond the two bugs the author already admits to.

## Mutation-survival list

1. Delete the `IF NOT (v_owner_trusted AND v_can_approve)` guard in the `exception` branch (`migrations/0002_shared_memory.sql:1071-1076`) — no test file references `op: "exception"` anywhere, so this authorization removal is invisible to the suite.
2. Delete the equivalent guard in the `release_dependency` branch (`migrations/0002_shared_memory.sql:1086-1091`) — same: zero tests exercise `release_dependency`.
3. Remove the `r.revision <> (entry ->> 'revision')::int` clause from `ar2_derived_valid` (`migrations/0002_shared_memory.sql:313-321`) — no test in `repo-cloud-*.test.mjs` ever sets `derived_from`/`derived_closure`/`dependency_release` on a created record, so stale-closure detection has no test surface at all.

## Compound lessons

1. A comment asserting "the DB is the real trust boundary" next to a `SECURITY DEFINER` function is a claim, not a proof — every dimension of the authorization matrix (here: `project_ids` scope, not just the `can_write` boolean) has to be independently verified against the matrix table, because it's exactly the dimension nobody wrote a test for that goes unenforced.
2. Client-side security transforms must be traced from the mutating call to the actual wire payload, not just to "a variable got reassigned somewhere above." A shallow-copied `cleanCmd` that's scrubbed and then never referenced again is invisible to any test that only inspects receipts — it takes reading the exact call site (`payloadHash(cmd, ...)` vs `payloadHash(cleanCmd, ...)`) to catch.
3. Skipping committed-RED tests doesn't just risk "the two bugs I happened to notice" — it removes the one mechanism that forces you to write the assertion *before* you know the implementation is right. Two admitted pre-commit catches plus at least four more defects found in one independent pass (project-scope bypass, dead scrub, missing exception-clear, unenforced closure cap) is the measured cost of that deviation, not a hypothetical one.
