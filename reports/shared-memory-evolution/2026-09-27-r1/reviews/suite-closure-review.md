## New defects

**G-handoff's new `commit_cursor` monotonicity check can spuriously fail a fully-compliant driver.**
`scripts/acceptance/contract-suite.mjs:1020-1023`:
```js
assert.ok(
  String(r1.commit_cursor) <= String(r2.commit_cursor) && String(r2.commit_cursor) <= String(r3.commit_cursor),
  ...
);
```
`commit_cursor` is typed `string` (opaque) in `packages/core/src/repository/contract.ts:226` — the contract does not require it to be a fixed-width or lexicographically-sortable numeric string. The bundled `naive-harness.mjs` itself implements it as `String(revision)` — i.e. exactly the pattern that breaks under lexicographic comparison once digit-width changes (`"100" <= "99"` is `false` as strings, despite 100 > 99 numerically). If a real driver's `commit_cursor` is a **global** monotonic counter (plausible: this same suite runs G-cas 100×2 writes, G-idem, G-authz's now-15 subtests, G-visibility's 1000+ reads/5-fixture-creates, G-existence, G-retract, and **G-derived's 257-source cap test** — all *before* G-handoff in file order) and that counter happens to cross a digit-width boundary across this test's 3 sequential checkpoints, a correct driver would spuriously fail here. I confirmed this new assertion was **never actually exercised** by the fix round's own verification: re-running the naive-harness self-test shows this subtest fails one assertion earlier (`containsId`, on `contract-suite.mjs:1001`, TAP output: `error: 'latestHandoff must return the newest (last-committed) checkpoint'`), so the commit_cursor line never even executes in the shipped self-test.
Required fix (small, non-blocking-severity but should land before real driver runs): either numerically parse cursors before comparing (`BigInt(r1.commit_cursor) <= BigInt(r2.commit_cursor)`, if the contract is amended to guarantee numeric cursors) or drop the commit_cursor assertion entirely and rely solely on the already-sufficient sequential-`await` happens-before ordering check.

(One incidental, pre-existing, non-blocking observation from probing #6: `egress-guard.mjs`'s patched `fetch` throws *synchronously* rather than returning a rejected promise, so a child process running `fetch(...).catch(...)` crashes instead of hitting `.catch`. Network is still fully blocked either way — not a security gap, not introduced by this fix round — just noting it since I exercised that code path directly.)
