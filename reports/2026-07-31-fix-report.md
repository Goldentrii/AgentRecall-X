## Deviations from the findings file

1. **Order**: implemented M8 before M7 (M7 consumes M8's `truncateUtf8Bytes` helper) — explicitly pre-approved in the work order ("M8 helper before M7 usage is fine to reorder — note it").
2. **H1 and M5 bundled**: both touch the same ~10-line archive-gate code block in `smart-recall.ts`. Implemented together but verified as two *independent* red→green pairs — each hunk was isolated (the other's fix temporarily reverted via a scratch copy) and re-tested alone to confirm each fails for its own stated reason before being restored together. See git diff for the combined final hunk.
3. **M6's red-test mechanism**: the findings file suggested "spy/count or filename trap." A `fs.readFileSync` monkeypatch (via `createRequire('fs')`) was attempted first and empirically does **not** intercept calls inside the compiled `packages/core` ESM dependency graph in this Node v24 environment — confirmed via an explicit identity check (`fs.readFileSync === require('fs').readFileSync` inside `resurrect.js` returned `false` after patching, vs. `true` in a minimal 2-file reproduction). Root cause not fully isolated (suspected: how Node's ESM facade for `node:fs` binds within this specific multi-hop import graph vs. a trivial one) and not worth further time given a clean alternative existed. Replaced with a genuine "filename trap": a card whose **filename** date is 400 days old but whose **frontmatter** `date:` field is forged in-window — before the fix this poison entry surfaced in `resurrect()`'s output (frontmatter date wins over filename date for the *existing*, unchanged post-parse cutoff check); after the fix the coarse filename pre-filter rejects the file before its frontmatter is ever read, so the forged date never gets a chance to matter. This is a strictly *stronger*, fully deterministic, monkeypatch-free proof of the same property (no window pre-filter) than a call-count spy would have been.
4. **Pre-existing test update (H2 side-effect)**: the existing `recency-index.test.mjs` test "rolls the ledger at 500 lines" asserted `lines.length <= 500` after 510 sequential appends from empty — an assumption invalidated by H2's intentional SLACK throttle (rolling no longer happens on *every* append past 500). Updated the appends-count to 560 and the assertion to `<= 550` (`MAX_LINES + SLACK`), with the reasoning documented inline. This is a deliberate consequence of the fix, not a regression.
