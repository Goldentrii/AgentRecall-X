## CHECK 1 — production semantics (fs-utils.ts): PASS

- Retry condition unchanged in kind: `process.platform === "win32" && (EPERM|EACCES|EBUSY)`.
  ENOENT/EXDEV/any other code, and all non-win32 errors, rethrow immediately on attempt 1.
- `RENAME_RETRY_BUDGET_MS = 5_000` exported; test imports it (verified old dist does NOT export it,
  so the export is genuinely new and the test derives from the real value).
- Backoff: 10 ms doubling, capped at 250 ms, and each nap is
  `min(delayMs, 250, budget − sleptMs)` — cumulative REQUESTED sleep lands exactly at 5000 ms,
  cannot overshoot. ~24 attempts worst case; `delayMs *= 2` growth is harmless (max ~1.7e8, no overflow).
  Sleep is `Atomics.wait` — no busy-spin.
- After the budget the error from the live rename attempt is rethrown; `code` preserved (RED run below
  surfaces the verbatim `EPERM ... rename ... .tmp.N -> ...` with `code: 'EPERM'`).
- Callers unchanged: diff touches only renameAtomic + comments; writeTextAtomic/writeJsonAtomic still
  call it at the same single choke point. No other src file in the diff.
- Worst-case latency judgment: these writers sit under check(), smart-recall feedback persist
  (inside the feedback-log lock), session_end, palace/index writes. A rename blocked the ENTIRE 5 s now
  stalls the caller synchronously 5 s instead of ~1 s — but that case is pathological: Node's own
  lock-free readers open with share-delete (they never block renames); real no-share-delete holders
  (AV/indexer) pin files 100 ms–2 s, i.e. inside the budget, and a released holder lands the write
  ≤250 ms later (the cap). Uncontended renames remain 1 attempt / 0 sleep. Lock interaction checked:
  a 5 s in-lock stall stays far under filelock's 60 s waitForLiveHolder cap, and the no-progress
  deadline extends while the same live holder makes progress — no steal path opens. Acceptable.

## CHECK 2 — test determinism: PASS

Reader script (read in full): `powershell.exe -NoProfile -Command`; opens with
`[System.IO.File]::Open(path,'Open','Read','Read')` (FileShare.Read — NO delete sharing);
`HOLDING` is written AFTER the open returns; `Start-Sleep` (the hold) starts after readiness.
Writer starts only once HOLDING arrives (promise gate). Startup failures are loud: spawn error
rejects, early exit without HOLDING rejects with stderr, 30 s startup watchdog kills + rejects;
single `settle()` gate prevents double-fire. Exit side: 30 s grace watchdog kills a wedged reader
in `finally` before afterEach's `rmSync`; testRoot removed per test.

- Transient: hold 1500 ms vs 5000 ms budget = 3.3× headroom (3.5 s of close-drift tolerance vs the
  >620 ms drift the CI runner showed, ~80 ms idle on this desktop). Landing time measured BEFORE the
  reader-exit await (correct — measuring after would mask a write that snuck through), asserted
  ≥ hold − 700 ms. The 700 ms epsilon is justified in the report: HOLDING→first-rename gap is a few
  syscalls (<100 ms loaded) and the reader's close only drifts LATE, so a sub-800 ms landing proves
  the window was never ridden out.
- No `took < budget` upper bound on the transient case (the brief expected one): its absence is
  CORRECT, and I would have flagged its presence. The budget counts requested sleep, so wall clock
  may legitimately exceed 5 s on a starved runner — a wall-clock `< budget` assertion would
  reintroduce exactly the runner-speed sensitivity A13 removes. The non-throw already proves the
  retry succeeded inside the requested-sleep budget.
- Persistent: hold = budget + 2500 ms; asserts EPERM via assert.throws, `took ≥ budget − 100`
  (clock-granularity guard; requested-sleep accounting makes wall ≥ budget), `took < hold − 1000`.
  Margin judgment: the 2.5 s split (≈1.5 s writer wall-overshoot allowance over ~24 naps + 1 s
  before release) is reasonable; the CI drift evidence (>620 ms on a 400 ms sleep) is a per-sleep
  absolute-delay effect, not proportional. assert.throws independently proves gave-up-while-held
  even if the explicit bound were ever grazed. See Notes (2) for the residual.
- Timeouts: transient 60 s, persistent 3 × (hold + budget) = 37.5 s — both ≥ 3× the longest in-test
  wait. Skip is a named string; node:test prints it (verified on Linux, below).
