## Item 1 — `bench-fixture.yml` step "Eval tests — latency + injection-size benches" (run 38230438759)

### Failure

2 of 22 tests failed on ubuntu-latest, both with
`FATAL: home-path leak detected in bench artifact` from the spawned child:

- `not ok 10` — latency.test.mjs e2e: `--n 12 --n-session 4` smoke
- `not ok 21` — session-start-size.test.mjs e2e: `--json --no-artifact` run on corpus-v1

### Root cause

Chain (pre-fix line numbers on main @ 9072d37):

1. Both e2e tests spawn the bench with an **absolute** `--store` path
   (`session-start-size.test.mjs:141`, `latency.test.mjs:139` — `CORPUS_V1 =
   path.join(HERE, "fixtures", "corpus-v1")`).
2. `resolveStore()` recorded that caller string verbatim as the artifact's
   `store` label: `scripts/eval/bench-lib.mjs:212`
   (`label: cliStore.split(path.sep).join("/")`).
3. The in-script leak gate (`session-start-size.mjs:309`, `latency.mjs:339`)
   is a pure substring regex: `scripts/eval/bench-lib.mjs:282`
   (`/\/Users\/|\/home\/|[A-Z]:\\+Users/`).
4. On GitHub runners the checkout lives **under HOME**
   (`/home/runner/work/AgentRecall-X/AgentRecall-X`), so the artifact's own
   store label is a `/home/` match → the child throws FATAL → exit 1 → test
   fails. Locally the repo sits outside HOME (`E:/tools`, checkout not under
   `C:\Users`), so the gate never fired — which is why 3.5.0 went out green.

The three later workflow steps (`--check-determinism`, latency smoke,
`bench:golden`) use the **default** store (relative label) and were not
affected; only the two absolute-`--store` e2e tests tripped.

### Fix (commit 12c4ec3, `scripts/eval/bench-lib.mjs` + tests)

a) **Artifact paths never absolute** — new `storeLabel(root)`: repo-relative
   forward-slash label for stores inside the repo, bare basename for external
   stores. `resolveStore(CORPUS_V1_abs)` now yields
   `scripts/eval/fixtures/corpus-v1`. `store_hash` disambiguates same-named
   external stores.

b) **Repo-root-aware guard** — `assertNoHomeLeak(json, { repoRoot })`:
   - extracts the full path token around each home marker
     (`/Users/`, `/home/`, `<drive>:\Users`), expanding left/right to JSON
     string delimiters (truncation fails CLOSED);
   - collapses separators, normalizes `..` segments, realpaths the token when
     it exists (symlink/junction safe), lowercases drive-lettered paths
     (NTFS case-insensitive; POSIX stays case-sensitive);
   - allows the candidate ONLY if it equals the repo root or sits below it
     (`repoRoot` injectable for tests, defaults to this checkout's root);
   - **any other path under a home dir still throws** — above all the real
     `~/.agent-recall`; string-prefix siblings (`<repo>-evil`) and
     `../`-escapes out of the repo are rejected.

Not touched (out of scope, both green on the runner): `run-bench.mjs`'s own
`assertNoHomeLeak` (checks written baselines, all relative) and
`golden-lib.mjs:findHomeLeak` (golden artifact records no store path). Flagged
for the reviewer: if either ever records a repo path, they need the same
allowance.

## Item 2 — `test (windows-latest)` lane (run 38230438655, core 1858/1860)

### 2a — audit-outcome-concurrency: materialized 290 vs ledger 480

**Root cause.** recordOutcome appends the lossless ledger line, then takes
`corrections-${project}` for the counter pass (`corrections.ts`, locked
section). On the starved 2-vCPU runner, a healthy holder descheduled for >5s
looks identical to a wedged one, so the A10 progress-aware deadline threw
`LockContentionError` and the caller's by-design reaction — skip the counter
pass — fired 190/480 times. With INCREMENT semantics
(`retrieved_count = stale + 1`), every skip was a permanently lost increment:
the ledger stayed complete (480) while the materialized counter froze at 290.

**Chosen fix: options (1) + (2) from the brief, combined.** Option (1) alone
is insufficient: skips cluster at the END of a starved run (hard-cap/wedged
expiry hits the back of the herd), and if the FINAL events' passes all skip,
no later pass exists to heal the counter before the at-rest assertion.
Option (2) alone fixes the test but leaves increment semantics one skip away
(60s cap, dead-holder edge) from silent divergence again. Together:

1. **Ledger-derived counters** (`corrections.ts`, recordOutcome locked pass):
   re-derive every counter-derived field from this correction's
   `_outcomes.jsonl` events via the EXACT replay core `ar outcomes rebuild`
   uses — `parseOutcomesLedger` → `sortForReplay` →
   `recomputeCorrectionCounters`, with the merge mirroring
   `runOutcomesRebuild`'s apply pass field-for-field. The counter is honestly
   a cache of the ledger (the test's old title said "may undercount" while
   asserting strict equality — retitled; assertion untouched, no tolerance
   band). Any skip now self-heals on the next successful pass.
2. **`waitForLiveHolder` lock mode** (`filelock.ts`, new
   `AcquireLockOptions`): recordOutcome's counter pass waits while the holder
   PID probes alive (dead holders still reclaim promptly; never-steal
   unchanged; unreadable-owner legacy locks keep the fixed timeout) instead
   of the wedged-holder heuristic. The 60s hard cap stays
   (`maxTotalWaitMs` overridable for tests). Hot paths keep the default 5s
   wedged detection; opting recordOutcome in is safe precisely because of
   fix 1 — even a cap-hit skip heals.

**Measurements** (lead-required): stress solo on this PC ~3.6s wall
(480/480); 3 concurrent copies (72 worker processes) all 480/480, total wall
5s; full core suite 3× consecutive green. 2-vCPU Linux container (the
faithful runner simulation) results in the verification matrix below.

### 2b — identity-trust-cwd-root-gate: 'prismma' instead of 'prismma-gateway'

**Root cause** (confirmed empirically, not the cross-drive hypothesis —
`path.relative` is not on this code path). GitHub's windows runner TEMP is
`C:\Users\RUNNER~1\…` — an 8.3 SHORT name ("runneradmin" > 8 chars).
`normalizePath` (`cwd-allowlist.ts`) used the JS `fs.realpathSync`, which
follows symlinks but passes 8.3 aliases through VERBATIM; on this PC:

```
js realpath : C:\Users\tong\AppData\Local\Temp\AR-SHO~1
native      : C:\Users\tong\AppData\Local\Temp\ar-shortname-probe-longname-dir
```

So the allowlist stored one spelling of the project root while
`git rev-parse --show-toplevel` produced the other, and the CRITICAL-2
directory-identity gate in `project.ts` (`normalizePath(ownToplevel) ===
hit.matchedPath`, strict string compare) failed → fell through to raw git
identity. Locally "tong" ≤ 8 chars → no short component anywhere → never
fired; ubuntu has no 8.3 names → passed.

**Fix** (`cwd-allowlist.ts` + `project.ts`):
- `normalizePath` prefers `fs.realpathSync.native` (resolves 8.3 aliases,
  junctions/symlinks, canonical on-disk case), falling back to the JS
  realpath, then the literal string.
- New `pathCompareKey`: case-folded on win32 (NTFS is case-insensitive),
  exact on POSIX. Every allowlist equality/prefix check (matchCwd exact +
  ancestor, the detectProject toplevel gate, addCwdToAllowlist dedupe) goes
  through it — raw string compares are gone from this path.
- `readCwdAllowlist` re-normalizes stored entries at read time, healing
  legacy short-name / stale-case entries with no migration step.

### 2c — surfaced while verifying: win32 transient-EPERM on atomic renames

During full-suite verification runs, `alignment-log-concurrency.test.mjs`
failed intermittently (2 of the first 5 suite runs) with
`EPERM … rename 'alignment-log.json.tmp.N' -> 'alignment-log.json'`.
Pre-existing, load-dependent, not caused by items 2a/2b (standalone 6/6 green
on main AND on this branch, even under artificial load — it needs full-suite
co-scheduling/AV timing): every atomic write is tmp+`renameSync`, readers are
deliberately LOCK-FREE, and on NTFS a rename OVER a destination any process
holds open without FILE_SHARE_DELETE fails EPERM for the life of the handle.
The helpers' own comments said "atomic on POSIX". Left unfixed it would keep
failing the windows CI lane sporadically — same class as this task.

Fix: `renameAtomic` in `fs-utils.ts` — bounded win32-only retry
(1→512ms backoff, ~1s total, then rethrow; POSIX renames over open files
succeed, so the retry path is unreachable there). Wired into
`writeTextAtomic`, `writeJsonAtomic`, and corrections' `writeRecordAtomic`.
Deterministic regression test (`fs-utils-rename-retry.test.mjs`): a
PowerShell child holds the destination with no delete sharing — reproduces
the production EPERM verbatim pre-fix; post-fix the write rides out a 400ms
hold, and a 3s hold still surfaces EPERM after the budget (bounded, never
wait-forever; old content intact).
