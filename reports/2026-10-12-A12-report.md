# A12 — alignment-log check() RMW: lost updates on starved runners

- **Date:** 2026-10-12
- **Branch:** `fix/alignment-log-rmw` (worktree `E:/tools/AgentRecall-X-a12`, base `main @ ebb6c58`)
- **Fix commit:** `293317b`
- **Trigger:** CI run 38242013300, `test (windows-latest)` lane, main @ ebb6c58:
  `packages/core/test/alignment-log-concurrency.test.mjs:105` — expected 40 records, got 11
  (29/40 alignment records lost). Ubuntu lane passed. Full log: `E:/tools/ci-run-38242013300-windows.log`
  (line 327: `records=11 unique_goals=11 lost_updates=29`, during the **Full test suite** step,
  i.e. the stress ran concurrently with all other packages' tests on 2 vCPUs).

## Root cause

Same failure class A11 fixed for `recordOutcome` (reports/2026-10-12-A11-report.md ITEM 2),
in a second caller. `check()` appends every alignment record through a locked
read→push→slice(-50)→write span on `alignment-log.json`
(`packages/core/src/tools-logic/check.ts:390`). On a starved 2-vCPU Windows runner a
perfectly healthy lock holder sits **descheduled** past filelock's 5 s no-progress
("wedged holder") deadline. The waiter misdiagnoses it as wedged, `acquireLock` throws
`LockContentionError`, and `check()`'s contention-skip branch logs + drops the record
(`alignment_log_skipped`). Under herd contention most calls take the skip path — 29/40
records lost in CI.

**Note on the test's own failure message** ("…with no lock; per-project file"): that
string was STALE — written when the test was the RED repro of the original
pre-fix6-locks unlocked RMW. Verified at main @ ebb6c58: `git show
ebb6c58:packages/core/src/tools-logic/check.ts` line 393 takes
`withLock("alignment-"+slug, …)` (added in `afd9b0a`), and the write was already
atomic (`writeTextAtomic` → A11's `renameAtomic`). The CI loss went through the
`LockContentionError` contention-skip branch, not an unlocked write. The stale
header + assertion message are corrected in `c9bf569` (diagnostic strings only; the
`strictEqual(goals.size, N*M)` invariant is byte-identical).

The decisive difference from `recordOutcome`: there is **no lossless ledger** behind
`alignment-log.json`. The file IS the store (readers: `readAlignmentLog` →
session-start briefing, `check()` similar_past_deltas, blind-spots derivation). A
skipped write is unrecoverable data loss, not a stale cache.

## Chosen fix (and alternatives)

**(1) `waitForLiveHolder` on the alignment-log RMW lock — chosen.**
`check.ts` now takes `withLock("alignment-"+slug, …, { waitForLiveHolder: true })` —
A11's opt-in: wait while the holder PID probes alive (and is from this boot);
dead-reclaim and never-steal unchanged; 60 s hard cap (`maxTotalWaitMs`). A
starvation misdiagnosis can no longer drop a record. The catch branch and the
`alignment_log_skipped` flag are **kept** as a loud last resort — now reachable only
past the 60 s pathological cap (or a crash lock whose owner record stays unreadable
~5 s) — because throwing there would lose the whole `check()` result on top of the
record, and the flag keeps the "never silent" LOW-3 doctrine intact.

**(2) Append-only jsonl with 50-cap at read/compaction — rejected for this task.**
Strongest (concurrent writers never RMW one file), but it is a format migration:
every reader of `alignment-log.json` (session-start briefing, check, nudge,
blind-spots-store, alignment-patterns, eval scripts, warroom doc) plus on-disk
back-compat. Not small. Listed as a follow-up hardening.

**(3) Both — rejected,** (1) already removes the data loss and measured wall-time
cost is nil (see timings).

## Lock-skip audit (every `LockContentionError` catch in packages/core/src)

| Site | What the skip loses | Loses durable data? | Action |
|---|---|---|---|
| `tools-logic/check.ts` (alignment-log RMW) | the alignment record — file is the only store | **YES** | **fixed: `waitForLiveHolder`** (this task) |
| `tools-logic/smart-recall.ts` `processFeedback` (feedback-log RMW) | the submitted feedback entries — `feedback-log.json` is the only store, nothing re-derives them | **YES** | **fixed: `waitForLiveHolder`** (same class, identical pattern; `feedback-log-concurrency.test.mjs` pins losslessness with strict `=== 120`; it was one starved run away from the same CI failure) |
| `storage/corrections.ts` `recordOutcome` | one materialized-counter pass — re-derived from `_outcomes.jsonl` on the next pass (self-healing) | no | already fixed by A11 (`waitForLiveHolder` + ledger-derived counters); skip kept correctly |
| `storage/corrections.ts` `setCorrectionTier` | one tier write — `tier` is a derived cache; next `ar corrections retier --write` recomputes it | no | keep skip (genuine best-effort cache) |

All other `withLock` callers have **no** catch: a `LockContentionError` propagates and
fails the operation loudly — no silent loss, out of scope. With this task every
lock-skip in the codebase either protects re-derivable state or is gated behind the
60 s pathological cap.

Note on smart-recall's old comment "never fail (or stall) a recall": with
`waitForLiveHolder` a *wedged-but-alive* holder can now stall `processFeedback` up to
the 60 s cap instead of 5 s (same trade A11 accepted for recordOutcome's callers,
session_start/session_end). A live, churning lock was always waited on; only the
rare alive-but-stuck holder pays more, and routine CI starvation no longer destroys
feedback entries. Flagged here for the reviewer explicitly.

## Error-path trace

1. **Holder dies mid-write:** `waitForLiveHolder` only extends the deadline while
   the pid probes alive — a dead holder stops extending, `tryReclaim` reclaims the
   lock dir promptly (unchanged). The victim's in-flight write was
   `writeTextAtomic` (tmp + `renameAtomic`), so readers never observe truncation;
   worst case is one orphaned `.tmp` file and that process's record dying with it
   (crash semantics unchanged).
2. **`process.exit()` inside the critical section:** release lives in `withLock`'s
   `finally`, which `process.exit` skips — leaves a dead-pid lock dir, reclaimed by
   the next waiter exactly as case 1.
3. **Corrupt `alignment-log.json`:** `readAlignmentLog` fails closed (`catch → []`,
   `helpers/alignment-patterns.ts:34`) — no crash; history resets and the next
   locked write rewrites a valid file. Pre-existing behavior, unchanged; combined
   with atomic writes this writer cannot produce a corrupt file itself.
4. **60 s pathological cap:** both writers keep the loud skip — stderr line + result
   flag (`alignment_log_skipped` / `feedback_log_skipped`), docs updated to say the
   flags are now pathological-cap-only.

## Review round — FIX 1+2 (reviewer-a12, reports/2026-10-12-A12-review.md) → `3476b9a`

Reviewer verdict: check() half PASS; smart-recall half FIX. 293317b made the
feedback persist lossless but left it **ahead of the search**, so a
wedged-but-alive feedback-log holder could block a feedback-carrying recall up
to the 60 s cap on the hot path (pre-fix worst case was 5 s + data loss).

**FIX 1 — persist off the critical path** (`smart-recall.ts`):
- Extracted `mergeFeedback` (pure; dedupe by id+query+date, slice(-1000)) —
  ONE implementation used by both the locked RMW (fresh locked read) and the
  new lock-free ranking merge, so ranking reflects this call's feedback with
  zero lock wait.
- The `waitForLiveHolder` locked persist (semantics unchanged) starts
  **before** the search and runs concurrently; `.catch` attached
  synchronously (no escaping rejection; non-contention errors log loudly and
  read as a skip when the race is won). Root scope: invoked inside the
  caller's AsyncLocalStorage context, which propagates through the whole
  continuation — the background completion writes to this call's
  `AGENT_RECALL_ROOT` (SDK two-instance isolation test in the suite).
- After results are assembled: `Promise.race(persist, 1 s grace)`. Settled →
  exactly as before (synchronous, accurate `feedback_log_skipped`). Still
  waiting → return immediately with new documented `feedback_log_pending:
  true`; the persist lands in the background once the holder releases (ref'd
  lock backoff timers keep a naturally-exiting process alive until the write
  completes — the strict 120/120 losslessness pin keeps holding; CLI recall
  never submits feedback, `cli/src/index.ts:581`, so no `process.exit` path
  strands a pending write). The grace timer is always cleared.

**FIX 2 — surfacing test asserts both contracts**: the smartRecall case now
pins recall `elapsed < 5 s` while the holder sits on the lock for 6.5 s
(`feedback_log_pending` visible, `feedback_log_skipped` absent) AND the entry
on disk after the holder releases (poll). check() case unchanged.

**TDD evidence**: new latency assertion RED on the pre-FIX1 build — recall
blocked 6768 ms (`a recall must never be blocked by the feedback write`);
