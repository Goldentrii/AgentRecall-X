## Findings

1. **MEDIUM · packages/core/src/helpers/alignment-patterns.ts:108-126, packages/core/src/tools-logic/smart-recall.ts:481-497 · no dedicated regression tests for the new parser/migration/compaction paths · FIX 1**
   `grep` over `packages/core/test` finds zero tests for: torn-tail/garbage-line tolerance of `parseAlignmentLogText`/`parseFeedbackLogText`, the legacy-array→NDJSON migration, the size-gated compaction (>1 MB → newest 50), or the read-time 50/1000 cap. The parsers are only exercised incidentally (tests reading freshly written NDJSON). Migration and compaction are the two remaining whole-file rewrites — the risky paths — and have no pin at all. I probed all four behaviors by hand and they work (table below), so the tests are a transcription job: legacy array + `check()` → NDJSON with old+new records; torn tail parsed=1 no-throw; garbage mid-line parsed=2 no-throw; 1.2 MB file → 50 lines, newest kept, oldest dropped; parser returns newest 50 of 600.

2. **MEDIUM · packages/core/src/helpers/alignment-patterns.ts:117-125, packages/core/src/tools-logic/smart-recall.ts:489-496 · lock-free fallback can run COMPACTION without the lock · FIX 2**
   `appendAlignmentRecord`/`appendFeedbackEntries` unconditionally run the size-gated compaction after the append. The contention fallback calls them WITHOUT the lock, so a fallback append on a >1 MB file performs a read→`writeTextAtomic` whole-file rewrite lock-free. A concurrent locked (or second fallback) append landing between that read and the rename is silently lost — the exact class this change exists to kill. The report's §8 wording ("only possible past a 60 s cap against a live compactor") understates the trigger: the fallback fires at the ~5 s no-progress deadline under wreckage, and during wreckage EVERY writer is a fallback writer, so two fallback appends can race each other's compaction with no 60 s involved. Not reachable in the CI test (40 records ≈ 100 KB « 1 MB) and rare in production (locked compaction keeps the file ~50 records), but the fix is ~5 lines: pass a `locked` flag from the call sites and skip compaction when false (compaction is pure optimization — deferring it is always safe). The legacy-migration branch in the fallback must stay as-is (a plain append onto an array file would poison the whole file for the dual parser AND the next migration would then drop the old records — the unlocked atomic merge is the only loss-bounded option; accepted residual, see Finding 6).

3. **LOW · packages/core/src/storage/filelock.ts:380-394 · tombstone write has no owner re-read guard · FIX 3**
   `release()` reads `owner` BEFORE `rmSync`, and on failure writes the tombstone with no re-check. If the releasing process is suspended >30 s between the `rmSync` throw and the `writeFileSync` (sync window, so suspension/debugger/swap only), the ownerless dir can be legacy-stale-reclaimed and re-acquired by a new holder B; the resumed releaser then overwrites B's live `owner.json` with `released:true`, making B's lock stealable mid-critical-section. Negligible probability, but `tryReclaim` already carries a TOCTOU restore guard for exactly this shape of race — a 2-line re-read (`skip tombstone unless ownerless or pid === process.pid`) matches the file's own paranoia standard.

4. **INFO · packages/core/src/storage/filelock.ts:369-373 · the rmSync retry sub-layer did not engage in the reproduced failure shape.**
   In my deterministic cwd-pin repro on the branch, `release()` returned in **1 ms** — `maxRetries: 10, retryDelay: 20` never rode out anything; the tombstone did 100% of the work. The comment's "rides out ms-scale pins for up to ~10*20ms" is aspirational for this EPERM shape. Harmless (the tombstone layer is the real fix), but the comment overstates the retry layer.

5. **INFO · torn-tail merge residual.** A partial append (ENOSPC mid-write, no trailing newline) makes the NEXT process's append concatenate onto the torn line — both records then fail `JSON.parse` and are dropped at read; the second loss is silent (its writer saw success). Optional hardening: append `"\n" + line` instead of `line + "\n"` — the parser already skips blank lines, and a leading newline guarantees a fresh line boundary regardless of what the tail looks like. Not required: the trigger needs a throwing partial write, which already flips the loud skip flag for the first record.

6. **INFO · legacy+contention double-corner (report §8, confirmed accurate).** Legacy array file + lock contention → unlocked atomic migration merge; two racing migrators = last-rename-wins, the loser's single record lost silently. Once per store lifetime at worst, gone after first successful migration. Accepted as documented; if tightening is wanted later, the fallback could skip-with-flag on legacy files instead of migrating, but that reintroduces a loud loss to avoid a silent one — judgment call, current choice is defensible.

## CHECK 1 — tombstone interleaving analysis

**Can a live holder ever be reclaimed? Effectively no — one negligible corner (Finding 3).** Trace:

- The tombstone is written only by the releasing holder itself, strictly AFTER its critical section completed (`release()` runs after the locked fn returns). Reclaiming a tombstoned lock therefore never interrupts a critical section.
- Race "A's rmSync fails because B re-created the dir": impossible — mkdir-based lock; if the dir still exists (rmSync failed), B's `mkdirSync` fails EEXIST and B never acquired.
- Race "rmSync partially succeeded (owner.json unlinked, dir pinned)": B's mkdir still fails EEXIST; waiters see an OWNERLESS dir with fresh mtime → not reclaimable for 30 s → nobody acquires in the microseconds before A's tombstone lands. A's tombstone then goes into a dir nobody holds. Safe.
- Race "dir vanished between rmSync-throw and tombstone write, B acquired fresh": for the name to vanish, someone must reclaim it; ownerless+fresh-mtime is unreclaimable for 30 s and A's pid probes alive, so this needs A suspended >30 s inside a 3-line synchronous window — Finding 3's corner, the only path by which a live holder (B) could later be stolen from.
- NTFS delete-pending: if rmdir succeeded-pending, rmSync does NOT throw (no tombstone path); mkdir on a delete-pending name gives EPERM, already handled as win32 contention (A10). No new exposure.
- `tryReclaim`'s existing rename-aside + captured-owner TOCTOU guard compares pid+acquired_at; the tombstone preserves both (pid = releaser = original holder, acquired_at carried over), so the guard's semantics are intact. The never-steal-from-a-live-holder test remains meaningful: `tryReclaim` still refuses any live, current-boot, non-tombstoned owner, and only the holder itself can mint a tombstone.
- `waitForLiveHolder` correctly excludes `released` owners from the deadline reset (filelock.ts:525-530), so waiters reclaim instead of waiting out a live-but-finished pid.

**Does the ownerless-wreckage path (no owner, no tombstone) still exist?** Yes — tombstone write can itself fail, and the mkdir→owner-write crash window remains. Behavior now: waiters still burn the 5 s no-progress deadline → `LockContentionError` → **but layer 2's lock-free append persists the record with no skip flag** (pinned by the new wreckage test in lock-contention-surfacing.test.mjs: elapsed ≥4 s proves the contention path, record on disk, `alignment_log_skipped` undefined). Heal is bounded by the 30 s mtime rule. The original CI bug (silent loss) is closed by layer 2 even where layer 1 can't fire. Verified.

## CHECK 2 — append atomicity and compaction

- Appends are one `appendFileSync` call (one line, or K joined lines for feedback) on an O_APPEND/FILE_APPEND_DATA handle. Atomic positioning is guaranteed; non-interleaving of the data for a single small write is not formally promised by Node docs on either platform, but is the observed NTFS/local-POSIX behavior, and the evidence here is direct: 40×~2.5 KB concurrent alignment appends and 120 feedback entries, zero torn lines, across 3 loaded Windows runs + 5 container runs + the worker's 10 starved runs. The parser's per-line try/catch makes a torn line a one-record loss, never a reader crash (probed: torn tail and garbage mid-line both skip cleanly, no throw).
- The fallback is taken only on `LockContentionError` (both call sites rethrow everything else), i.e. at the 5 s no-progress deadline or the 60 s cap.
- Compaction: under the lock it is exclusive against all locked writers, and `writeTextAtomic` (tmp+rename) keeps lock-free READERS safe. The 50-cap semantics survive: cap is enforced at read time always, physically at compaction time; my probe compacted 1.2 MB/600 records → exactly 50 newest lines, newest record kept, oldest dropped. The one hole is the fallback-triggered lock-free compaction (Finding 2). **In the CI scenario it loses nothing** (file size is two orders of magnitude under the gate); as a class it should still be closed because it is cheap to close.
