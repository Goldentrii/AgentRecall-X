## 2. Per-failure root cause and fix

### 2.1 destination-proof ×8 (class a — test setup not case-hermetic) → 2d4d0fd
- Suite: `packages/core/test/identity-trust-completeness.test.mjs` (destination-proof describe, subtests 8, 9, 10, 12, 13, 15, 17, 19).
- Single root cause: `REAL_SLUG = "AgentRecall"` is deliberately mixed-case. `sanitizeProject` lowercases (`src/storage/paths.ts:89`), and the resolver's existing-dir reuse rule (`resolveProjectDirName`, `src/storage/paths.ts:166`; naming-v2 §2) picks the raw-case directory only when it already exists. The suite's `beforeEach` wipes `projects/`, so a bare `core.ensurePalaceInitialized(REAL_SLUG)` scaffolded the SANITIZED `projects/agentrecall/` tree while the tests hand-joined `projects/AgentRecall/...`. One inode on case-insensitive Windows/macOS (suite always passed); two silently-diverging trees on Linux — fixture writes ENOENTed (subtests 8/9/10/12) or planted files no reader resolved (13/15/17/19). Subtests 1–7 passed on Linux only because their journal helpers `mkdirSync` the raw-case dir first, flipping the resolver to the raw-case branch — which is exactly the state the fix pins.
- Fix (test setup only): new `initPalaceRaw(slug)` helper pre-creates the raw-case project dir before `ensurePalaceInitialized`; all 12 call sites in the suite routed through it. Security assertions byte-for-byte unchanged.

### 2.2 fix7 embeddings config.json ×1 (class b — code) → 5b57af7
- Test: `fix7-embeddings.test.mjs:438` "(g) config.json embeddings_enabled" — "corrupt config reads as off, never throws" got `true`.
- Root cause: `embeddingsEnabled()`'s config cache (`src/embeddings/config.ts`) was keyed on `mtimeMs` alone. The test deletes config.json and rewrites it corrupt within the same timestamp tick on fast Linux; the cache served the stale pre-delete `enabled: true`. The code's own doc promised "edits are picked up on the next call via the mtime key" — not honored.
- Fix: cache key is now `ino:size:mtimeMs:ctimeMs` (all free from the statSync already performed). Delete/recreate changes ino; content edits change size and/or ctime.

### 2.3 updateIndex mtime ×1 (class b — code) → abc74a3
- Test: `journal-index-incremental.test.mjs:107` "DOES re-read a file whose mtime is newer than the index's last-write time".
- Root cause: `updateIndex` (`src/helpers/journal-files.ts:409`) used `fileMtimeMs <= indexMtimeMs` as the cache-hit rule. On the container filesystem's coarse timestamp tick, the rewrite landed exactly equal to the index's last write and the stale cached row survived — the code's documented "known limitation" made user-visible by CI.
- Fix: strict `fileMtimeMs < indexMtimeMs` (equal = ambiguous = re-read; the make-style conservative choice). The companion cache-hit test pins its file 60 s before the index, unaffected. The incremental-equals-full-rebuild regression test still passes.

### 2.4 recordOutcome concurrency ×1 (class c — race, fixed in code) → 9df166e + cd68ce9
- Test: `audit-outcome-concurrency.test.mjs` — 24 processes × 20 `recordOutcome('retrieved')`; materialized count must equal the lossless ledger (480). Observed 476/480 Linux, 461/480 Windows baseline.
- Root cause: NOT an unlocked RMW — `recordOutcome` has held `withLock("corrections-<project>")` since 2026-07-25. The losses came from `acquireLock`'s fixed `now + 5s` deadline (`src/storage/filelock.ts`): it measured TOTAL wait, so under heavy-but-healthy contention (480 short critical sections serializing through one lock) back-of-herd waiters threw `LockContentionError`, and recordOutcome's documented contention handler skips the materialized-counter update — each spurious timeout silently lost one increment.
- Fix: progress-aware deadline. The 5 s timeout now bounds time with NO observed progress (owner pid+acquired_at unchanged — a wedged holder, the timeout's actual job) and resets whenever the lock changes hands; `MAX_TOTAL_WAIT_MS = 60s` hard-caps the absolute wait. Never-steal semantics, dead-holder reclaim, pre-boot reclaim untouched; the filelock suite's live-holder test still times out at ~5 s (its holder never changes).
- Follow-up (cd68ce9): the higher acquire/release churn exposed a Windows NTFS corner — mkdir of a delete-pending lock dir throws EPERM, which `tryAcquire` rethrew as an environment error, crashing 1/24 stress workers. win32-only: EPERM now means "contended, retry"; POSIX keeps the strict rethrow.
- Stability (reworded per review FIX 2 — Windows determinism was overclaimed): **Linux CI is deterministic 480/480**. **Windows is reduced from a deterministic loss to a low-frequency load flake**: baseline lost 4-19 increments EVERY run; post-fix the reviewer saw 478/480 under full-suite load and 479/480 in 1 of 3 solo runs, while idle runs are 480/480 (3/3 on this branch, 3/3 again post-merge). Mechanism is the designed contention-skip: under CPU starvation a holder can sit >5 s without releasing (indistinguishable from wedged) or a waiter hits the 60 s cap; the ledger stays lossless and `ar outcomes rebuild` repairs. A2's recommendation stands for A8's Windows CI: serial lane / timeout bump for the two child-process stress suites.

### 2.5 sync-errors ×2 (class a — test env assumption) → 89a6354
- Test: `sync-errors.test.mjs` — expected the log under `$HOME/.agent-recall/`.
- Root cause: `logSyncError` resolves through `getRoot()` (`src/supabase/sync.ts:81`, the 2026-07-31 root-fix): `setRoot()`/`AGENT_RECALL_ROOT` override first, homedir fallback last. The suite only overrode HOME, so any runner exporting `AGENT_RECALL_ROOT` (the documented isolation that keeps tests out of the real `~/.agent-recall`) redirected the log elsewhere and both assertions failed — Windows baseline and Linux non-root alike.
- Fix (test setup only): `setRoot(tmpHome/.agent-recall)` in before(), `resetRoot()` in after(). Assertions unchanged. Also removes 2 Windows-baseline failures.
