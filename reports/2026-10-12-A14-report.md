## 2. Evidence

### CI signature (run 38255969731, E:/tools/ci-run-38255969731-windows.log)

- `records=12 unique_goals=12 lost_updates=28`, all 10 workers exited 0 (the strictEqual fired, not a worker crash — so no renameAtomic exhaustion, which throws).
- `duration_ms: 21764` for the test. Reconstruction: ~1.5 s barrier + ~12 serialized RMWs under starvation (~5-7 s) → wreckage event → every subsequent waiter burns ~5 s (ownerless dir: `waitForLiveHolder` resets the deadline only when it can read a live owner) → `LockContentionError` → skip; each child's remaining 2-3 calls × ~5 s ≈ 21-22 s. The 60 s cap and the 30 s mtime stale rule were both out of reach inside 21.8 s — which is why the wreckage never healed within the test.

### Deterministic mechanism proof (this machine, win32)

`release()` while the lock dir is pinned (child process with CWD inside it — the same NTFS `rmdir → EPERM` state an antivirus/indexer directory scan produces on a CI runner):

```
ARLOCKDBG {"ev":"release-failed","errno":"EPERM","dir_still_exists":true}
after release(): dir_exists= true
waiter THREW LockContentionError after 60191 ms — check() would SKIP (silent loss)
```

The release failure was previously swallowed with zero trace. A same-process `fs` handle does NOT reproduce it (Node/libuv opens with `FILE_SHARE_DELETE` and modern NTFS uses POSIX delete semantics — the unlink succeeds instantly); an external no-delete-share pin (AV/indexer/CWD) does.

### Why run #3 passed and run #4 failed

The wreckage needs `rmSync` to collide with an external pin in a ms-scale window — probabilistic. A13 (5 s rename-retry budget spent *inside* the lock, synchronous `Atomics.wait`) lengthened holds, increasing both runner AV pressure and the number of waiters polling at each release. Same coin as reviewer-A13's feedback-log 2/120 residue under heavy local load (reproduced here, §4).

### Local reproduction attempts (stochastic)

10 children + 6 CPU-spinner processes all pinned to 2 logical cores (PowerShell `ProcessorAffinity=3`), test root under the Defender-scanned `%TEMP%`: pre-fix build survived 5/5 (the wreckage collision did not land on this machine — local Defender configuration differs from the runner's). The CI-shape evidence therefore comes from the deterministic mechanism proof + the 21.8 s timing reconstruction + the shipped instrumentation (the next CI loss prints the full per-call/per-lock-event table, §5).

## 3. Fix (two layers — the class, not the instance)

### Layer 1: filelock release robustness (`packages/core/src/storage/filelock.ts`)

- `release()` now calls `rmSync` with `maxRetries: 10, retryDelay: 20` (rides out ms-scale pins).
- If removal STILL fails: writes a **tombstone** into `owner.json` (`released: true`) and reports it on stderr — never silent. A tombstoned holder has provably finished its critical section, so:
  - `tryReclaim` reclaims a tombstoned lock immediately, regardless of pid liveness;
  - `waitForLiveHolder` no longer waits on a tombstoned owner.
  The lock self-heals the moment the external pin lifts (measured: ~2.0 s pin → acquire at 2.5 s, vs pre-fix 60 s cap → skip).
- `tryAcquire`'s owner-write failure (the other producer of the "held but ownerless" signature) is now logged via the debug channel.

### Layer 2: the write shape (structural) — append-only NDJSON

`alignment-log.json` (and `feedback-log.json`, §4) are now **append-only NDJSON**: one scrubbed JSON object per line (`appendAlignmentRecord` in `packages/core/src/helpers/alignment-patterns.ts`).

- The locked path appends one line (`appendFileSync`); migration from the legacy array format and size-gated compaction (>1 MB → newest 50) are the only whole-file rewrites and stay behind the lock.
- On `LockContentionError`, check() now **appends WITHOUT the lock** instead of dropping the record. Append-vs-append is lossless by construction; the only writer that could race it (migration/compaction) runs behind the very lock that just timed out, i.e. is not running. `alignment_log_skipped` now fires only if the append itself throws (disk full/EACCES).
- Bonus: the hot path no longer rewrites/renames the file per check(), so A13's 5 s in-lock rename-retry storms against lock-free readers are gone and holds collapse to one small append.
- Readers: ONE shared dual-format parser (`parseAlignmentLogText`, exported) — legacy array files still parse; the 50-cap moved from write time to read time. Updated callers: `readAlignmentLog` (session-start, blind-spots, check), CLI stats counter, 5 test files, 2 eval scripts (`capture-discard-backfill`, `capture-gate-confusion`). `content-guard` cleanliness is preserved (scrub runs per line before the write).

## 4. Feedback log — same class, fixed, not just explained

Reviewer-A13's residue reproduced locally **after** the Layer-1 fix: starved ×5 → `118/120` in 2 of 5 runs (one call's K=2 entries lost to the skip branch). So the skip-converts-pathology-to-loss class was still live for `feedback-log.json`, and "explain" would have been a cop-out. Applied the same structural fix in `smart-recall.ts`:

- `parseFeedbackLogText` (dual-format + read-time dedupe of id-carrying entries by query+id+date, keep-first — mirrors the old write-time rule — cap 1000, exported);
- `appendFeedbackEntries` (locked append; legacy migration; 2 MB-gated compaction);
- `newFeedbackEntries` extracted as THE dedupe rule; `mergeFeedback` (ranking path) delegates to it — one implementation, no drift;
- contention → lock-free append fallback; `feedback_log_skipped` only if the append throws.

Post-fix starved ×5: **120/120 every run** (table below).

## 8. Residual risks (documented, accepted)

- Lock-free fallback append racing a compaction: only possible past a 60 s cap against a live compactor mid-rewrite — a vanishing corner, strictly better than the guaranteed loss it replaces.
- Fallback append onto a never-migrated legacy array file: the one double-corner (legacy file + first post-upgrade write + lock contention) does an unlocked atomic whole-file merge — the pre-A12 racy behavior, once per store lifetime at worst.
- Tombstone write itself blocked (dir pinned with no write share): reclaim falls back to the 30 s mtime rule — but the data is safe either way (append fallback).
- `.json` extension now holds NDJSON content. Kept deliberately: every path reference (user stores, warroom, eval scripts) survives, and the shared parser reads both formats. Flagged for the orchestrator in case a rename-with-migration is preferred later.
