## FIX items

1. **MEDIUM · packages/core/src/tools-logic/smart-recall.ts:946 (processFeedback, 424–474) · feedback persistence sits ON recall's critical path and can now block the whole recall up to 60 s · move it off the critical path, keep losslessness.**
   `smartRecall()` awaits `processFeedback` at line 946 *before* the search dispatch (line ~962 onward) and before result assembly (line 1177); ranking consumes the returned log. With `waitForLiveHolder` the locked RMW inside it waits out a live holder up to filelock's 60 s hard cap, so a recall that submits feedback serializes a potentially-60 s lock wait ahead of producing any result. Pre-fix worst case was a 5 s stall (plus data loss); post-fix worst case is 60 s. Recall is the product's headline hot path (README.md:81, :94 — recall p95 209 ms).
   **Required design** (both contracts must hold — lossless under contention AND recall never blocked by the feedback write):
   - Rank THIS call from a lock-free `readFeedbackLog()` merged in-memory with the submitted entries (equivalent to today's post-RMW log reuse, no lock wait needed for ranking).
   - Start the persist promise — `withLock("feedback-log", rmw, { waitForLiveHolder: true })`, unchanged semantics — *before* launching the search so it runs concurrently; attach a `.catch` that logs loudly *before* any race (no unhandled rejection; a past-cap `LockContentionError` stays loud on stderr).
   - After results are assembled, `Promise.race([persist, grace ≤ 1 s])`. Normal case: the lock is uncontended and persistence completes during the search — zero added latency, `feedback_log_skipped` reporting stays synchronous and accurate. Raced-out case: return results immediately with a documented `feedback_log_pending: true` (persistence continues in the background up to the 60 s cap).
   - Losslessness holds without extra plumbing: the lock wait's ref'd backoff timers keep a naturally-exiting process alive until the persist settles, which is exactly how `feedback-log-concurrency.test.mjs` children exit (no `process.exit` on success), so its strict `=== 120` keeps passing. The CLI never submits feedback (`packages/cli/src/index.ts:581` passes query/project/limit only), so no `process.exit` path can strand a pending write; SDK embedders calling `process.exit` immediately lose only that call's entries — same crash semantics as today's in-flight write.

### FIX 1 verified by reading (smart-recall.ts)

- **No double-persist.** `mergeFeedback` is pure (`log.slice()`, never mutates) and the ONLY write site remains the locked RMW inside `processFeedback` (`writeTextAtomic` on the fresh locked read). Settled → `feedback_log_skipped` reporting is synchronous and exact, as before; raced out → documented `feedback_log_pending: true`, mutually exclusive with the skip flag. The one reporting gap — raced-out persist that LATER hits the 60 s cap is stderr-only (the result already returned) — is documented honestly in the interface comment; unavoidable, acceptable.
