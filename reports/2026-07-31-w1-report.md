## F1b — truncation-direction finding (empirical, done BEFORE coding)
Read the real fixture archive file (`~/.agent-recall/projects/novada-mcp/journal/archive/raw/2026-07-31--8a02c8b2-*.md`, read-only) and measured it directly: body is exactly 80,000 chars, and the underlying bug is in `readTranscriptByPath()`'s `rawTail` construction — `readHeadTail()` was called with defaults (head=60K, tail=25K), concatenated (`${head}\n…\n${tail}`, ~85,003 chars), then `.slice(0, 80_000)` — which keeps chars `[0, 80000)` of the CONCATENATION. Since head alone is 60,000 chars, this keeps **all** of head (stale boilerplate) and only the first ~19,997 of the 25,000-char tail, silently dropping the **last ~5,000 chars of the file** — exactly where decisions/next-steps live. Confirmed: the archived fixture body ends mid-JSON (`"usage":{"input_tokens":2,"cache_creat`), consistent with a hard cut mid-record.

Fix: a dedicated second `readHeadTail(filePath, 20_000, 60_000)` read for `rawTail` only (small head sample, large tail preserve); if the combined string still exceeds the 80K cap, trim is taken from the **start**, never the end (`combined.slice(combined.length - RAW_TAIL_CAP)`). The pre-existing `head`/`tail` read (defaults 60K/25K) used for `cwdGuess`/`firstUserMessage`/`recentExchanges`/`projectGuess` was deliberately left untouched — those fields' consumers are outside my scope, and shrinking head there risked regressing first-user-message detection in sessions with heavy startup boilerplate. Cost: one extra bounded file read per call; correctness over micro-perf.

Test: `transcript-reader.test.mjs` — a synthetic >200K-char fixture with a marker at the true end (survives) and a marker in the dropped middle gap (correctly absent). Used a synthetic fixture, not the real file, since the real file lives outside the repo and would make the suite non-portable/flaky in CI.

## F3 — session-card.ts
`buildSessionCard({rawHead, rawTail, meta}) → {markdown, title, artifacts, linearRefs, decisions, nextStep, sid, slug, date}` + `writeSessionCard(card)`. Pure-mechanical, wrapped in try/catch (never throws — degrades to a minimal valid card on malformed input, tested). `writeSessionCard` writes `journal/<date>--card--<sid>.md` (a normal journal file, per design), atomic tmp+rename, idempotent on session id (mirrors `archive-write.ts`'s convention), sid/slug sanitized via `sanitizeSlug` before any `path.join`.

Card size cap (~2KB) enforced in **UTF-8 bytes**, not chars — this repo's content is routinely CJK-heavy, and a char-based cap would silently blow well past 2KB on disk for Chinese-heavy sessions (exactly this fixture's shape).

Acceptance test (`session-card.test.mjs`): built from a **synthetic** fixture reproducing the real incident's essential shape — see CHALLENGE #2 below — asserts the card contains both `TOW2-357` and `交付物2_MCP原型_V14.html`, plus 10 more unit tests (title fallback, artifact precision, decision/next-step extraction, linearRefs dedup, frontmatter fields, error-path, empty-boilerplate-only session, write/idempotency/traversal-safety).

## CHALLENGE — deviations from the compiled design (flagged, not silently worked around)

1. **linearRefs regex is wrong in the design doc, fixed.** Spec: `/[A-Z]{2,6}-\d+/g`. Verified empirically: `"TOW2-357".match(/[A-Z]{2,6}-\d+/g)` → `null`. The digit `2` inside the real team-key prefix (`TOW2`, team "TongWu") breaks an uppercase-letters-only character class before the hyphen is ever reached — this regex would have silently failed on the exact ID this feature exists to capture, in this exact codebase's own convention. Widened to `/\b[A-Z][A-Z0-9]{1,5}-\d+\b/g` (must start with a letter, then 1-5 more alphanumerics, then `-digits`) — verified it still rejects `HEAD`, version strings, and lowercase tokens.
2. **F3's acceptance fixture is synthetic, not a literal read of the real incident file.** The real fixture (`~/.agent-recall/projects/novada-mcp/journal/archive/raw/2026-07-31--8a02c8b2-*.md`) is (a) outside the repo — unsafe/non-portable for an automated CI suite to depend on, and (b) itself a snapshot produced under the OLD buggy F1b truncation, so its own final record (containing both required strings) is cut off mid-JSON and would be **skipped** by any lenient per-line JSON parser — it literally cannot exercise the fixed tail-preserving path. I also confirmed the underlying live `.jsonl` transcript (`~/.claude/projects/-Users-tongwu/8a02c8b2-*.jsonl`) has grown from ~85KB (at archive time) to 817KB since — it's a live, continuously-updated file, not a frozen fixture, reinforcing that depending on it directly would be wrong. Built a synthetic fixture instead, documented prominently in the test file's header comment.
3. **linearRefs scan scope widened** beyond a literal "final assistant text" reading: scans the full JSON of every non-boilerplate user/assistant record (not just its extracted "text" block), so IDs embedded in tool_use inputs (e.g. a `remember()` call's content, as happens in the real incident) are still caught — still boilerplate-excluded, so this doesn't reopen the false-positive class the fixture report warned about.
4. **F1b uses a second, separate file read** rather than changing `readHeadTail()`'s shared defaults, to avoid touching `readTodaySessions()`'s unrelated firstUserMessage/cwdGuess extraction (outside my scope, other consumers depend on the existing 60K/25K balance).

None of these conflict with the SUCCESS_WHEN acceptance criteria — all are documented inline in code comments (marked "NOTE (CHALLENGE...)" in `session-card.ts`) as well as here.
